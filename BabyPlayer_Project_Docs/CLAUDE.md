# Claude Code Project Rules

## 1. 当前项目阶段

当前项目处于：

**需求分析与冻结阶段。**

在用户明确回复：

**“冻结需求”**

或具有相同含义的明确指令之前，禁止：

- 编写正式业务代码；
- 初始化最终工程结构；
- 决定最终技术架构；
- 大规模生成文件；
- 提前实现未来功能。

当前允许：

- 阅读项目文档；
- 分析需求；
- 查找需求冲突；
- 提出必要的澄清问题；
- 调研 Apple / tvOS 平台限制；
- 帮助收敛 MVP；
- 分析不同实现路径，但不得自行替用户冻结方案。

---

## 2. 开发总原则

需求冻结并进入开发后：

1. 不破坏已有功能。
2. 不进行未经要求的大规模重构。
3. 不为了代码“更优雅”进行额外抽象。
4. 不修改当前任务没有涉及的代码。
5. 每个开发阶段项目都必须保持可运行。
6. 一次只完成一个明确任务。
7. 禁止偷偷增加需求。
8. 禁止提前开发“以后可能会用”的功能。
9. 优先选择简单、稳定、容易维护的实现。
10. 任何复杂设计都必须说明它解决的实际问题。

---

## 3. 需求变更规则

开发过程中出现新的想法时，不要立即实现。

先判断：

- 是否属于当前 V1？
- 是否影响当前核心闭环？
- 是否会扩大当前任务范围？

如果不是当前任务必须完成：

记录到 Backlog。

不得顺手实现。

---

## 4. 修改前规则

每次准备修改代码之前，先说明：

- 本次目标；
- 涉及文件；
- 为什么需要修改；
- 可能影响什么；
- 如何验证。

确认任务边界后再修改。

---

## 5. 修改范围

每次只处理当前明确任务。

例如当前任务是“实现首页媒体卡片”，不得顺便：

- 重构播放器；
- 修改无关数据模型；
- 重做设置页面；
- 引入新的架构；
- 更换无关依赖。

如果当前任务确实无法独立完成，先说明阻塞原因。

---

## 6. 代码与注释规范

代码文件开头需要说明：

1. 文件用途；
2. 当前文件的主要功能；
3. 最近一次修改目的。

每个独立功能块前说明：

- 功能职责；
- 输入；
- 输出或副作用。

每个函数需要说明：

- 函数职责；
- 关键参数；
- 是否影响共享状态、UI 或数据。

本次新增或修改的重要代码位置使用：

`【MODIFIED】`

并说明修改目的。

不得删除已有有效注释。

---

## 7. 状态与解耦

- 每个函数尽量只负责一件事。
- 避免隐式依赖。
- 不在函数内部偷偷读取全局状态。
- 必须共享的状态集中管理，并说明生命周期和影响范围。
- 不为未来可能出现的需求提前抽象。

---

## 8. Git 与回滚

开发保持小步修改：

**一个独立任务 → 验证 → 一个清晰提交**

不得将多个无关功能混入同一修改。

任何阶段都应该能够安全回滚到上一个可运行状态。

---

## 9. 文档优先级

所有实现必须服从已经冻结的产品需求。

发生冲突时：

**用户最新明确指令 > PRODUCT.md > TASK.md > 当前代码实现**

如果发现文档之间存在冲突，不自行猜测，应先指出冲突。

---

## 10. Claude Code 的职责

Claude Code 的工作流程：

**理解项目 → 分析任务 → 确认边界 → 定位代码 → 最小修改 → 验证 → 汇报**

Claude Code 的职责不是：

**重新设计整个项目。**

---

## 11. 完成任务后的自检

每次完成实现任务后检查：

- 所有新增函数是否有必要注释；
- 所有关键修改位置是否有 `【MODIFIED】` 标记；
- 项目是否仍可运行；
- 是否修改了任务范围外的代码；
- 是否能够安全回滚；
- 三个月后重新阅读是否能够快速理解。
