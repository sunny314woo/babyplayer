# BabyPlayer — 完整需求分析（需求冻结前）

> 状态：需求分析阶段，尚未冻结。用户明确确认“冻结需求”前，禁止正式编码、生成最终工程结构或自行确定未确认方案。

## 1. 产品定义

BabyPlayer 是一个面向幼儿家庭的 Apple TV 本地儿童媒体播放器。

它不是另一个 VLC，也不是要做成 Infuse/Plex 一类通用家庭媒体系统。核心目标是把“本地儿童媒体文件”变成孩子可以理解和选择的“内容”。

核心体验：

**打开 App → 看到熟悉的大封面 → 选择 → 播放**

家长负责准备和配置内容；儿童负责浏览和播放。

## 2. 要解决的问题

### VLC
VLC 能播放大量格式，但文件/目录概念明显、入口较多、操作偏工具化，UI 也不是儿童内容消费型。孩子很难独立找到自己想看的内容。

### Infuse
Infuse 的内容优先、大封面和 Apple TV 媒体库体验值得参考，但主要围绕电影、电视剧和成人媒体库设计。

BabyPlayer 不和它们比较“支持多少格式”，而比较：

**孩子能不能更容易找到并播放内容。**

## 3. 目标用户

### 家长
负责媒体准备、首次配置、必要的内容管理和设置。复杂技术概念如果无法消除，只允许出现在家长路径。

### 幼儿
主要面向约 1～6 岁儿童。儿童负责浏览、识别封面、选择、播放和基础退出/切换，不需要理解文件路径、IP、服务器、SMB/NFS 等概念。

## 4. 产品原则

1. **内容优先**：首页首先展示可播放内容，不首先展示设置、文件夹或服务器。
2. **儿童优先**：高频儿童路径优先于低频家长配置。
3. **家长配置，儿童消费**：底层复杂性不得暴露给儿童。
4. **少层级**：理想路径是“首页 → 内容 → 播放”。
5. **封面优于文件名**：儿童主要依靠视觉识别。
6. **Apple TV Remote 优先**：围绕 tvOS Focus 设计，不把手机 UI 简单放大。
7. **严格控制范围**：新功能必须直接改善“找到内容 → 选择 → 播放”，否则进入 Backlog。

## 5. 核心业务闭环

家庭已有儿童媒体
→ 家长完成一次媒体来源配置
→ BabyPlayer 获取媒体
→ 形成儿童可识别的内容/封面
→ 儿童打开 Apple TV App
→ 首页直接展示内容
→ 遥控器移动 Focus
→ 点击封面
→ 播放
→ 退出或播放结束后返回内容界面。

V1 必须完整跑通这条链路。

## 6. 当前最大的需求分歧：媒体来源

### 版本 A：Mac 作为媒体来源

**核心目标**：儿童媒体主要存在 Mac，Apple TV 在家庭局域网访问 Mac 上准备好的媒体。

**适用边界**：家庭已有 Mac；家长习惯在电脑整理资源；播放期间 Mac 可以保持可访问。

**V1 不做**：NAS、路由器 U 盘、云盘、多服务器、多协议、互联网远程播放。

**取舍与风险**：
- 优点：媒体整理方便，产品范围容易控制，封面/元数据后续处理方便。
- 风险：Mac 是否必须开机、局域网发现、断线体验、是否需要 Mac 配套程序，以及 tvOS 权限/限制需要验证。

**MVP**：一个指定媒体位置 → Apple TV 能发现 → 展示 → 播放。

**长期方向**：验证成功后再考虑友好的 Mac 配置端、自动发现、索引、封面处理和多目录。

**快速验证**：先做技术 Spike，只验证 Apple TV 能否稳定发现并播放 Mac 提供的一个测试视频，不做正式 UI。

### 版本 B：Apple TV 直接访问家庭存储

**核心目标**：媒体位于家庭长期在线存储，Apple TV 直接访问，尽量不依赖 Mac。

**适用边界**：家庭已有共享存储，希望 Mac 关闭后仍可播放。

**V1 不做**：一次实现大量协议和设备兼容，只选择一条最小链路。

**取舍与风险**：
- 优点：播放不依赖 Mac，更接近长期家庭媒体设备。
- 风险：配置容易重新变成 VLC 式网络播放器；不同路由器/NAS 带来兼容性和测试矩阵；项目容易膨胀为通用媒体客户端。

**MVP**：选择一种明确来源，完成“配置 → 发现 → 展示 → 播放”。

**长期方向**：真实需求出现后再增加媒体来源。

**快速验证**：使用真实家庭存储测试访问、列举、播放稳定性和配置复杂度。

### 当前不自动选择 A/B

| 对比 | A：Mac 来源 | B：家庭存储直连 |
|---|---|---|
| 家长整理内容 | 简单 | 取决于设备 |
| 播放时依赖 Mac | 可能 | 否 |
| V1 范围 | 较可控 | 容易扩大 |
| 配置复杂度 | 可隐藏 | 容易暴露网络概念 |
| 最大风险 | 服务/发现链路 | 兼容性/范围膨胀 |

## 7. V1 功能需求草案

### FR-01 首次启动与家长配置【待冻结】
家长完成一次媒体来源配置。完成后儿童日常启动不重复配置。媒体来源不可用时必须有明确反馈。具体流程依赖 A/B 选择。

### FR-02 儿童首页【方向确定】
打开 App 后直接看到儿童内容。大封面、少文字、不首先展示文件系统；支持 tvOS Focus；焦点明显；点击直接播放。具体布局由 Figma 冻结。

### FR-03 内容分类【待冻结】
内容较多时提供简单分类。候选包括横向分类行、少量大分类入口或主题内容组，例如儿歌、动画、睡眠、ABC、角色/系列。V1 不做 AI 分类。

### FR-04 媒体获取【核心阻塞】
Apple TV 稳定获取家长准备的媒体；儿童不参与；失败不应卡死；媒体变化后存在合理更新方式。具体机制依赖 A/B。

### FR-05 最小媒体信息【方向确定】
每个内容至少具有唯一标识、显示名称、封面、媒体位置和基础媒体类型。不提前建立复杂元数据系统。

### FR-06 封面【方向确定，细节待冻结】
优先使用已有可用封面；没有时生成稳定的默认视觉封面，可考虑视频抽帧。不得要求家长逐个手工制作。生成失败有占位图。生成位置需要技术验证。

### FR-07 视频播放【方向确定】
支持开始播放、暂停/继续、退出、合理返回、播放失败反馈和符合 tvOS 习惯的遥控器操作。V1 不堆专业播放器控制项。

### FR-08 播放进度/继续播放【待冻结】
需要决定 V1 是否记录上次位置，以及儿童内容默认更适合“从头播放”“自动继续”还是两者都提供。

### FR-09 独立音频【待冻结】
决定 V1 仅支持视频，还是同时支持 MP3/M4A 等纯音频。如果儿歌资源主要是视频，独立音频库可以延后。

### FR-10 家长设置【存在确定，范围待冻结】
低频家长入口可能包含媒体来源、刷新/扫描、基础内容管理。不能占据儿童首页主要位置。是否需要家长锁等机制待确认。

### FR-11 空状态【确定】
无媒体时不能展示空白首页，应告诉家长当前没有内容以及下一步操作。

### FR-12 媒体源离线【确定】
不得无限 Loading 或崩溃；提供家长可理解的提示和重试入口。

### FR-13 Figma 设计【确定】
正式 SwiftUI 实现前至少确认首次配置、儿童首页、Focus 状态、分类/浏览、播放、返回、空状态、媒体源不可用和家长入口。Figma 同时用于冻结 Apple TV Remote 的交互流，而不只是视觉稿。

## 8. 非功能需求

- **简单**：儿童高频路径尽可能保持“打开 → 选择 → 播放”。
- **稳定**：局域网波动和媒体不可用不能导致崩溃。
- **性能**：首页不能因实时重处理长时间等待；封面等重任务避免阻塞浏览。
- **可维护**：不提前抽象；V1 不同时支持多协议；小步提交；每阶段可运行、可回滚。
- **隐私**：没有明确需求前，不把儿童媒体上传第三方云服务。
- **tvOS 原生体验**：必须考虑 Focus、Remote、电视观看距离、大点击区域、返回行为和系统播放器习惯。

## 9. V1 明确不做

- AI 推荐/分类/故事生成；
- AI 识别儿童兴趣；
- 根据生活照片生成内容；
- 在线儿童视频平台/YouTube 聚合；
- 账号体系；
- 商业授权/支付；
- 云同步；
- 社交；
- 多家庭成员账户；
- 儿童成长档案；
- 复杂观看统计；
- 推荐算法；
- 一次支持大量网络协议；
- 为未来需求预建复杂服务器架构。

## 10. UI 需求方向

### 首页
大封面、大间距、少量清晰分组；Focus 后明显突出；电视距离下仍容易识别。

### 文字
儿童可能不识字，标题只能辅助，不能成为唯一识别方式。

### 颜色
儿童化不等于大量高饱和颜色。优先保证内容突出、焦点明确、页面干净。

### 动效
主要服务 Focus、点击反馈和页面切换。V1 不做纯装饰性的复杂动画。

## 11. 数据流

家庭媒体存储
→ 媒体发现/扫描
→ 最小媒体信息
→ 封面获取/生成
→ Apple TV 内容界面
→ 用户选择
→ 播放器获得媒体
→ 播放
→ 可选记录播放状态。

当前最大未知点是：

**媒体存储 → Apple TV 获取。**

## 12. 业务逻辑自检

**核心业务是否闭环？**
产品层面闭环；技术/操作层面尚未完全闭环，因为媒体来源未冻结。

**数据从哪里来、流向哪里？**
家庭已有儿童媒体 → BabyPlayer → Apple TV 播放器。是否经过 Mac 配套端待确认。

**是否存在先写但不知道怎么用的模块？**
禁止。账号、AI、推荐、云端、通用媒体服务器、多协议抽象层均不得提前开发。

**哪些功能可以延后？**
AI、推荐、云同步、多用户、复杂媒体管理、复杂统计等全部延后。

## 13. 主要风险

1. **变成另一个 VLC/Infuse**：不断增加协议、文件浏览、格式和设置会失去儿童播放器定位。
2. **过早写漂亮 UI**：媒体链路未验证就大量实现 UI，底层方案变化会造成返工。
3. **把配置复杂度转给儿童**：底层复杂性必须由家长路径吸收。
4. **封面处理过度复杂**：V1 要的是稳定可识别的封面，不是 AI 选出“最好的一帧”。
5. **一次支持太多媒体来源**：显著增加网络兼容、错误处理、测试和维护成本。

## 14. 建议阶段（不是最终开发计划）

### Phase 0：需求冻结
确定媒体来源、数据链路、Mac 端是否存在、视频/音频范围、分类、播放进度和家长设置边界。

### Phase 1：技术 Spike
只验证最大风险：真实 tvOS/Apple TV 能否通过选定链路稳定播放一个本地媒体。此阶段不追求 UI。

### Phase 2：Figma
冻结页面、Focus、Remote 交互、页面流转和异常状态。

### Phase 3：最小播放器闭环
实现“媒体 → 首页 → 点击 → 播放 → 返回”。

### Phase 4：必要完善
只补影响 V1 使用的问题：空状态、断线、封面、必要设置和必要播放状态。

### Phase 5：真实家庭测试
Apple TV 真机 + 真实电视 + 真实儿童媒体环境测试。优先修体验和稳定性，不立即增加新功能。

## 15. 需求冻结前必须回答

1. **媒体主要放在哪里？** Mac、路由器 U 盘、NAS，还是其他？
2. **V1 是否接受播放时 Mac 必须在线？**
3. **V1 是否需要独立 Mac 配套 App？** 还是接受更轻量的本地服务/配置方式？
4. **V1 是否只做视频？** 还是必须同时支持纯音频？
5. **内容分类由谁决定？** 文件夹即分类、家长分类、固定分类或其他简单规则？
6. **继续播放是否属于 V1？** 默认从头、自动继续，还是两者都有？
7. **家长设置如何进入？** 既容易被家长找到，又不干扰儿童。
8. **首次配置允许多大技术复杂度？** 应尽量隐藏，但需要明确可接受边界。

## 16. 当前需求结论

当前已经明确的产品方向：

> **BabyPlayer 是儿童优先的 Apple TV 本地媒体播放器。**
>
> **价值不是支持更多媒体格式，而是让儿童以最少操作，通过视觉封面找到并播放家庭已有内容。**
>
> **家长负责配置，儿童负责浏览和播放。**
>
> **V1 只解决最短闭环，不建设通用家庭媒体平台。**

当前最高优先级：

**确定 V1 媒体来源和 Apple TV 获取媒体的链路。**
